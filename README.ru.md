# netspeed

English version: [README.md](README.md)

Измеряет скорость скачивания с этой машины: последовательно запрашивает
один URL несколько раз и показывает среднюю пропускную способность.

## Что измеряется

- **Скорость** — байты тела, делённые на время передачи тела. Фаза
  заголовков (DNS, TCP, TLS) исключена, поэтому медленное рукопожатие
  не искажает результат.
- **TTFB** — время от начала запроса до получения заголовков ответа;
  показывается отдельно.
- **Единицы** — `MiB/s` — это `1024**2` байт в секунду, что многие
  инструменты называют «MB/s»; `Mbit/s` — это `10**6` бит в секунду.
  Печатаются обе величины, потому что «MB/s» сам по себе неоднозначен.
- **Статистика** — по умолчанию 10 последовательных запросов. Отчёт
  показывает среднее время запроса, среднее из скоростей отдельных
  прогонов (главная величина, которую требует задание), сводную
  скорость (`total bytes / total measured time` — общее число байт,
  делённое на суммарное измеренное время), которая отличается от
  среднего, когда прогоны передали разный объём, а также медиану,
  минимум, максимум и выборочное стандартное отклонение; для
  единственного прогона отклонение указывается как неприменимое.

Каждый измеренный прогон переиспользует одну `requests.Session`,
поэтому DNS, TCP и TLS происходят один раз, а прогоны делят одно
keep-alive соединение — при условии, что цель держит соединение
открытым и не отвечает перенаправлением. За ответом `3xx` клиент
следует прозрачно: дополнительные round-trip'ы попадают в фазу
заголовков (TTFB) и в среднее время запроса, но не в знаменатель
скорости, которым служит время тела; измеряется тело конечной цели, а в
отчёте остаётся запрошенный URL; сервер же, отвечающий
`Connection: close`, обходится в одно соединение на прогон. Первым
отправляется один дополнительный прогревочный запрос, который
исключается из статистики.

## Как считается объём

- Запрашивается `Accept-Encoding: identity`, поэтому сервер, идущий
  навстречу, отдаёт тело без сжатия, и посчитанные байты — это байты,
  реально переданные по сети (и ничего сверх них: ни заголовков, ни
  кадрирования chunked).
- Сервер, который всё же сжимает, измеряется, но тогда считается
  *распакованный* размер; прогон помечается предупреждением в stderr и
  считается непроверенным по размеру.
- Когда сервер присылает `Content-Length`, а в ответе нет ни кодирования
  содержимого, ни кодирования передачи, полученный размер обязан
  совпасть с ним точно. Короткая передача прерывает всё измерение с
  кодом выхода 1 вместо того, чтобы попасть в среднее как удачный
  прогон. Сравнение охватывает байты, прочитанные клиентом: сервер,
  который продолжает писать сверх собственного `Content-Length`,
  засчитывается лишь до объявленного размера, а излишек отбрасывается
  непрочитанным — клиент не может это заметить без второго пробного
  чтения.
- Заголовок `Transfer-Encoding` имеет приоритет над противоречащим
  `Content-Length`, как требует RFC 9112, раздел 6.3. Кадрирование
  chunked проверяется HTTP-слоем, поэтому обрезанное chunked-тело
  прерывает прогон (код выхода 1); любое другое кодирование оставляет
  размер непроверенным.
- Тело, ограниченное закрытием соединения (в стиле HTTP/1.0, без
  кадрирования) и оборвавшееся раньше времени, обнаружить нельзя: без
  пригодного `Content-Length` прогон принимается с предупреждением, а в
  отчёт добавляется примечание, что размер не удалось проверить.

Тело читается потоком порциями по 64 KiB и никогда не удерживается в
памяти целиком, поэтому файл на много гигабайт — безопасная цель.

## Требования

Python 3.10 или новее и пакеты из `requirements.txt`.

## Установка

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Использование

```sh
# 10 измеряемых запросов плюс отброшенный прогрев
python netspeed.py https://speed.cloudflare.com/__down?bytes=25000000

# 5 запросов, таймаут сокета 30 секунд, без прогрева
python netspeed.py -n 5 -t 30 --no-warmup https://example.com/big.jpg

# машиночитаемый вывод
python netspeed.py --json https://example.com/big.jpg

# подробности по прогонам и трассировки в stderr
python netspeed.py -v https://example.com/big.jpg

# через прямой прокси; краткая запись host:port означает http://
python netspeed.py -p http://proxy.com:3128 https://example.com/big.jpg

# прокси с учётными данными; они уходят на прокси, но печатаются как ***
python netspeed.py -p http://user:pass@gproxy.com:3128 https://example.com/big.jpg

# SOCKS-прокси, например демон Tor; нужен пакет PySocks
python netspeed.py -p socks5://127.0.0.1:9050 https://example.com/big.jpg

# то же через удалённый DNS (для Tor рекомендуется): имя резолвит
# сам прокси
python netspeed.py -p socks5h://127.0.0.1:9050 https://example.com/big.jpg
```

Опции: `-n/--runs` (1..1000, по умолчанию 10), `-t/--timeout` (до 3600
секунд, по умолчанию 15), `--chunk-size` (до 16 MiB, по умолчанию
64 KiB), `--no-warmup`, `-p/--proxy`, `--json`, `-v/--verbose`.
`--runs` и `--chunk-size` — целые числа, `--timeout` — десятичное число
секунд; ведущие нули лишь дополняют разрядность и не меняют значение.

По умолчанию измерение идёт напрямую, а переменные окружения прокси
(`http_proxy`, `HTTPS_PROXY`, …) игнорируются, так что действующий
маршрут — всегда тот, что назван в командной строке. Опция
`-p/--proxy` направляет каждый запрос через указанный прокси (цель
`https://` туннелируется через него методом `CONNECT`), а отчёт и JSON
называют прокси, заменяя любой `user:password` в нём на `***`. Прокси
должен работать по HTTP или по одному из вариантов SOCKS, и к нему
применяются те же правила хоста и порта, что и к аргументу URL;
негодный прокси — это ошибка аргументов ещё до первого запроса.
Краткая запись `host:port` считается HTTP-прокси, поэтому SOCKS-узлу
(скажем, демону Tor на `127.0.0.1:9050`) нужна явная схема — лучше
всего `socks5h://`, где имя резолвит сам прокси. Явные схемы
`socks5://` и `socks4://` резолвят имя на этой машине, из-за чего
прокси может получить адрес, выбранный для этой сети и недоступный с
его стороны; когда такой прогон падает, отчёт советует писать
`socks5h://` или `socks4a://`. Для SOCKS дополнительно нужен пакет
`PySocks`, и транспортная ошибка называет его, если зависимости нет.

`--timeout` — таймаут сокета, применяемый к попытке соединения и к
каждому чтению, поэтому он ограничивает простой, а не общую
длительность прогона: сервер, отдающий по байту за раз, может
удерживать один прогон дольше таймаута. Используйте большой файл и
разумное значение `-n`, иначе результат измерения будет бессмысленным.

Учётные данные в URL (`http://user:pass@host/file`) используются для
запроса, но заменяются на `***` в отчёте, в JSON и в каждом сообщении об
ошибке, включая те, что цитируют отвергнутый аргумент. Сокрытие
работает по принципу отказа в сторону сокрытия: при сомнении оно
скрывает лишнее, а не недостающее (*fails closed*). Скрываются:

* учётные данные, набранные без схемы (`user:pass`), в виде значения
  опции или разбитые пробелом между аргументами — тогда аргументы вокруг
  куска с разделителем скрываются вместе с ним, вплоть до следующего
  целого URL вида `scheme://`, который остаётся читаемым, потому что это
  самая полезная часть сообщения;
* аргумент, начало которого лишь похоже на схему (`user:pass://host`):
  он считается учётными данными, а не URL;
* текст, начало которого не является схемой: он скрывается целиком, как
  только содержит двоеточие или знак `@`, потому что и то, и другое
  может быть потерянным `user:password`;
* разделители, записанные в процентном кодировании
  (`alice%3ASECRETpw%40host` и дважды закодированное написание): они
  раскодируются, причём повторно, до этой проверки; текст, в котором
  процентное кодирование не стабилизируется за отведённые проходы, тоже
  скрывается;
* аргумент-URL, у которого последний знак `@` лежит вне компонента
  authority (хоста с необязательным портом), например, `?u=user@secret`
  или путь вида `mail@example.com`: он скрывается целиком, потому что
  знак `@` читается как разделитель учётных данных в любом месте; когда
  он является настоящим userinfo (учётными данными в URL), текст за ним
  подчиняется тем же правилам, поэтому повторённый там пароль тоже
  скрывается, как только он несёт собственный разделитель; написание без
  разделителя входит в три слепые зоны, перечисленные ниже;
* аргумент-URL, содержащий пробельные символы, и URL с двоеточием вне
  authority, например, запрос или фрагмент вида `?u=user:pass`;
* authority, который не является ни хостом без порта, ни хостом с одним
  портом в диапазоне `1..65535` (порт нечисловой, вне диапазона или
  пустой), ни authority со вторым двоеточием, как в
  `http://alice:pw:8080/x`; IPv6-литерал подчиняется тому же правилу
  внутри своих скобок, поэтому `http://[::1]:user:pw/x` тоже скрывается.
  Такой URL отклоняется ещё до запроса: инструмент выдаёт ошибку
  аргументов (usage), называет правило порта и никогда не повторяет сам
  аргумент;
* значение, принадлежащее опции: отделённое (`-n secret`), присвоенное
  (`--runs=secret`), приклеенное к известному флагу (`-vsecret`,
  `-vvsecret`) или дописанное к имени известной опции (`--jsonsecret`); а
  также значение, отвергнутое инструментом, — оно цитируется только
  тогда, когда каждый его символ мог быть частью запрошенного числа;
* любые сведения о транспорте, сообщённые библиотекой: `-v` удерживает
  их всякий раз, когда URL пришлось скрывать, потому что такие сведения
  могут процитировать учётные данные без их схемы.

Три варианта записи невозможно распознать одной лишь синтаксической
проверкой, и все их лучше избегать: голый секрет, у которого нет ни
двоеточия, ни знака `@`, — неважно, стоит ли он отдельно
(`netspeed.py URL SECRET`), приклеен к неизвестной опции (`-xSECRET`)
или лежит в пути, запросе либо фрагменте, закодированный или нет;
числовой пароль, читающийся как допустимый порт, например,
`http://alice:1234`; и разделитель, записанный похожим символом,
например, полноширинным двоеточием. Неизвестная опция нарочно остаётся
читаемой, чтобы опечатка вроде `--jsno` всё равно была названа в
ошибке. Избыточное сокрытие лишает вывод схемы, хоста или пути; полный
URL сохраняется только в самом запросе.

Текст, который присылает сервер, экранируется, а не печатается как есть:
значения заголовков `Content-Encoding` и `Transfer-Encoding`, значение
`Content-Length` и фраза-пояснение (`reason phrase`) в строке статуса
неудачного ответа. Поэтому враждебный сервер не может управлять
терминалом через `-v`. Когда URL несёт учётные данные, эти значения
заголовков удерживаются целиком, а не просто экранируются: сервер-цель
получает этот userinfo как basic-аутентификацию и может вернуть его в
ответе, поэтому ничто из присланного сервером не считается заведомо
свободным от учётных данных.

## Пример вывода

```
URL: https://speed.cloudflare.com/__down?bytes=25000000
Runs measured: 3 (warm-up excluded)

  #        MiB   TTFB s   body s  basis s      MiB/s     Mbit/s
  1      23.84    0.040    1.974    1.974      12.08      101.3
  2      23.84    0.039    2.210    2.210      10.79       90.5
  3      23.84    0.036    2.239    2.239      10.65       89.3

Summary
  total downloaded: 75000000 bytes (71.53 MiB)
  mean TTFB:        0.038 s
  mean body time:   2.141 s
  mean request:     2.179 s
  mean of runs:     11.17 MiB/s = 93.7 Mbit/s
  aggregate:        11.13 MiB/s = 93.4 Mbit/s (total bytes / total measured time)
  median:           10.79 MiB/s = 90.5 Mbit/s
  min / max:        10.65 / 12.08 MiB/s
  std deviation:    0.79 MiB/s
```

`mean request` — среднее время запроса (TTFB плюс время тела), которое
требует задание. `basis s` — время, реально взятое в знаменатель: время
тела или, в редком случае, когда тело пришло вместе с заголовками и
время тела измерить не удалось, полное время запроса.

`--json` печатает те же величины машиночитаемо: URL, по объекту на
прогон с числом байт, фазами, объявленным размером, флагом проверки и
обеими скоростями, плюс сводку и использованные единицы.

Выбирайте файл хотя бы в несколько мегабайт: на маленьком файле
измеряется задержка, а не пропускная способность, и числа ничего не
значат.

## Коды выхода

| Код | Значение |
| ---- | ------- |
| 0 | Измерение выполнено |
| 1 | Не удался запрос или ответ (ошибка транспорта, 4xx/5xx, пустое тело, несовпадение размера, неизмеримый прогон) либо отчёт не удалось записать |
| 2 | Непригодные аргументы (URL без схемы http(s), непригодный порт, плохие `--runs`, `--timeout`, `--chunk-size` или `--proxy`) |
| 130 | Прервано пользователем (Ctrl-C) |

Неудачный прогон прерывает серию; частичное среднее не печатается.

## Тесты

```sh
source .venv/bin/activate
pip install -r requirements-dev.txt
pytest
flake8 .
isort --check-only --diff .
black --line-length 79 --check --diff .
mypy .
```

Набор тестов поднимает локальный HTTP-сервер и локальный прямой прокси
на эфемерных портах, поэтому сеть ему не нужна. Тот же сервер можно
запустить вручную как цель измерения — это удобно на машине без доступа
в интернет:

```sh
python tests/http_server.py --port 8123
# в другом терминале
python netspeed.py -n 3 http://127.0.0.1:8123/payload
```

Прокси проверяется так же:

```sh
python tests/http_proxy.py
# в другом терминале
python netspeed.py -n 3 -p http://127.0.0.1:<порт> http://127.0.0.1:8123/payload
```

## Состав файлов

```
netspeed.py                 CLI для измерений
tests/http_server.py        локальный сервер-цель для тестов
tests/http_proxy.py         локальный прямой прокси для тестов
tests/conftest.py           фикстуры pytest (сервер, прокси, URL эндпоинтов)
tests/test_netspeed.py      набор тестов
setup.cfg                   настройки flake8 и isort
requirements.txt            зависимость времени выполнения
requirements-dev.txt        инструменты для тестов и линтеров
```

Тесты выполняются в виртуальном окружении `.venv`, которое `.gitignore`
держит вне системы контроля версий.
